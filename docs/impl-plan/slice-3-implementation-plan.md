# Slice 3 implementation plan

HR can create a drive, upload a job description and a batch of resumes, correct and confirm candidate records, and review shared L1 and L2 skills. Directors can inspect a read-only drive overview. The slice is complete when this workflow passes on the local Mac stack with synthetic records. [Requirements roadmap](../core/requirements-roadmap.md#3-let-hr-prepare-a-drive) · [Product plan](../core/product-plan.md#drive-setup-and-interview-preparation)

## Scope and access

| Action | HR | Director | Panelist |
| --- | --- | --- | --- |
| Open Drives, list all drives, see names, intake counts and the L1/L2 skills and review state | Yes | Yes, read-only | No |
| Create a drive, set or replace the job description, upload resumes, edit and confirm candidates, resolve duplicates, change or review skills | Yes | No | No |
| Read intake rows, candidate contact details or extraction suggestions, and download original files | Yes | No | No |

Use the role returned by the existing verified staff session. All HR users share the drive workspace. The creator and uploader are recorded for audit. Mount the drive API under `/api/staff/drives` and reuse the session, approved-domain, origin, and cache controls from Slice 2. Check the current role before any drive data query, upload body processing, or S3 call. Resolve each child resource within the requested drive, including downloads and duplicate targets. Return `401` unauthenticated, `403` for a denied role, and `404` for a nonexistent record or an ID from another drive after the role check. Give Directors a narrow overview response constructed from explicitly selected fields. Filter the sidebar with the same read-role policy. Send a signed-in Panelist opening a drive URL directly back to Dashboard and show no drive data. [Current staff authorization](../../apps/server/src/staff/routes.ts) · [Staff access rules](../core/product-plan.md#people-and-access)

Slice 4 handles booking, invitation links, and assignment-specific panelist access. Slice 5 freezes scorecards per attempt. Slice 9 adds AI suggestions. Keep this slice local, use deterministic extraction with synthetic documents, and defer hosted AI, OCR, real candidate data, and Dokploy. [Requirements roadmap](../core/requirements-roadmap.md)

## Implementation order

### 1. Add shared contracts and drive storage

- Add Zod contracts for drive inputs and responses, upload metadata and status, candidate draft and review actions, scorecard skills, and stable error codes. Keep candidate email validation separate from staff-domain validation. Give all records server-generated IDs and use checked foreign keys for relationships. Add a forward Drizzle migration, preserve existing fixtures and staff, and provision a dedicated `document-intake` queue alongside the storage probe through the existing migration service. Start and verify the app's non-migrating pg-boss producer before serving intake requests, close it during shutdown, and register a separate bounded consumer in the worker. [Schema](../../apps/server/src/schema.ts) · [Migration entry point](../../apps/server/src/migrate.ts) · [App entry point](../../apps/server/src/main.ts)
- Store a drive’s name, creator, timestamps, JD revision, and active JD document ID. Give documents a drive-scoped reference, kind, uploader, original filename, declared and validated content types, size, SHA-256, unique opaque object key, and upload and parse states. Ensure the active JD points to a document from the same drive and check its kind when updating the pointer. Record the upload attempt, deadline and cleanup status. Enforce one candidate per accepted resume with a unique source reference and same-drive foreign key. Add indexes for list ordering, pending work, and source lookups.
- Store editable candidate fields for name, email, and optional years of experience, with review state `draft`, `confirmed`, or `duplicate`. Use a write revision for concurrent edits. Store normalized email after trimming and lowercasing. Enforce one **confirmed** candidate per normalized email per drive with a PostgreSQL partial unique index. Drafts may collide. The same email in different drives represents independent candidacies. Enforce same-drive relationships for candidate sources and duplicate targets in the schema and service. [PostgreSQL partial indexes](https://www.postgresql.org/docs/current/indexes-partial.html)
- Store one ordered skill set per drive and round with stable skill IDs, a write revision, and review metadata. Trim names and reject empty or repeated names within each round. Let HR reorder and edit the set, then explicitly mark a nonempty set reviewed. Any subsequent edit invalidates that round’s review. These are drive-level defaults that Slice 5 can snapshot.
- Add an idempotent, opt-in synthetic drive seed alongside the storage probe fixture. Associate it with a verified local HR fixture account, using the existing Mailpit registration and Director grant flow in isolated acceptance setup. Include small text PDF, DOCX, and scan-only fixtures for tests. Keep credentials and real names or addresses out of fixture files. [Local seed](../../apps/server/src/seed.ts)

### 2. Build the HR API and make upload completion recoverable

| Endpoint under `/api/staff/drives` | Purpose |
| --- | --- |
| `GET /`, `GET /:driveId` | Paginated drive list and overview for HR and Directors |
| `POST /` | Create a named drive for one hiring requirement |
| `POST /:driveId/documents` | Accept a job description or one resume, return its durable intake status |
| `GET /:driveId/documents`, `GET /:driveId/documents/:documentId/original` | HR-only paginated intake, bounded status lookup by document IDs and original downloads |
| `GET /:driveId/candidates`, `PATCH /:driveId/candidates/:candidateId` | Review queue and candidate draft edits |
| `POST /:driveId/candidates/:candidateId/confirm`, `POST /:driveId/candidates/:candidateId/duplicate` | Explicit review actions |
| `PUT /:driveId/skills/:round`, `POST /:driveId/skills/:round/review` | Save ordering and explicitly review one round |

Use the existing global error handling for unexpected errors and structured codes for expected validation, permission, conflict, and dependency failures. Paginate drive and intake lists with stable ordering and bounded limits. A save with an outdated revision returns `409` and current safe fields so HR can reload without losing their local edits. Make drive creation retriable with a client-generated idempotency key scoped to the creating staff account. A replay with the same normalized name returns the same drive, and a changed payload returns `409`.

- Send one raw file body per request. Use `?kind=job_description|resume`, a percent-encoded UTF-8 `X-Upload-Filename` header, `Content-Type`, `Idempotency-Key`, and `X-JD-Revision` for JD uploads. Cap and validate metadata before reading the body. Allow a missing or generic declared MIME when the extension and validated structure agree. The browser wraps multi-select in a client-side queue so each file succeeds or fails independently. After authorization and admission, stream the body into a private temporary file within a 30-second deadline, count bytes independently of `Content-Length`, and hash in the same pass. Verify the PDF signature or inspect the bounded DOCX central directory for `[Content_Types].xml` and `word/document.xml`. Leave decompression to the worker. Missing, mismatched, oversized or unsupported files get a field-specific `400`, `413` or `415` and leave no candidate or S3 object. Clean staging files on success, cancellation and failure, and sweep stale files after restart. [Hono body limits](https://hono.dev/docs/middleware/builtin/body-limit) · [yauzl entry validation](https://github.com/thejoshwolfe/yauzl#openpath-options-callback)
- Reserve a pending database record and an immutable object key before the S3 write. Store under a dedicated drive-upload prefix and persist a unique idempotency tuple of uploader, drive, kind, and client key. Match the digest and normalized metadata on replay. A completed replay returns `200` with existing IDs, an in-flight replay returns `202` with its document ID for the HR status lookup, and a mismatched replay returns `409 idempotency_conflict`. An expired or failed reservation returns `409 upload_retry_required` so the browser can offer a new attempt. Use the same key while the outcome is uncertain and a new object key for each new attempt.
- After the object write succeeds, atomically mark the original stored, create its candidate shell if it is a resume, and enqueue the intake job. Check that the reservation is still pending, the attempt matches and its deadline has not elapsed. Use pg-boss’s installed `fromDrizzle` transaction adapter, require a job ID, and persist it for restart recovery. For a JD replacement, compare and increment the JD revision in the same transaction and retire the previous original only when the new pointer commits. Reject a conflicting replacement and make its intermediate object eligible for cleanup. [pg-boss transaction adapter](https://github.com/timgit/pg-boss/blob/master/src/adapters/drizzle.ts) · [Storage architecture](../core/architecture.md#private-file-storage)
- Use a row lock or compare-and-set so publication and cleanup cannot win for the same attempt. The cleanup task must transition an expired, failed or unreferenced superseded attempt to a terminal cleanup claim in PostgreSQL **before** deleting its object. Recheck the current JD and candidate references under that guard. Retry interrupted or unsuccessful deletes idempotently and keep tombstones long enough to reconcile a late object write under the dedicated prefix. Keep the fixture prefix outside cleanup. Run bounded sweeps at app startup and periodically using the app’s existing bucket-scoped identity, as SeaweedFS 4.55 maps object deletion to its write capability. Keep the parsing worker’s storage identity read-only. Verify against the pinned image that the app can clean up its objects and that anonymous and worker mutations are denied. [SeaweedFS 4.55 S3 routing](https://github.com/seaweedfs/seaweedfs/blob/4.55/weed/s3api/s3api_server.go#L1125) · [AWS SDK for JavaScript S3 client](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/client/s3/)
- Stream downloads through the authorized Hono route after checking drive, document, and object state. Return the validated media type, a safe attachment filename with encoded UTF-8 support, `nosniff`, and private no-store caching. Never return keys or S3 credentials to browsers. Accepted originals remain downloadable when extraction fails. Distinguish a missing object or storage outage from a missing database record without exposing storage internals.

### 3. Add bounded text extraction and explicit candidate review

- Add `pdfjs-dist@6.5.438`, `mammoth@1.13.0`, and ZIP validation with `yauzl@3.4.0` in the server workspace. Verify the proposed pins and the PDF.js legacy Node import inside the runtime image. Run a text PDF, DOCX, and scan-only PDF through the parser before integrating it with the API. For PDF, use bytes and page text extraction and release the loading task. For DOCX, use Mammoth raw text with external file access disabled. In the parser child, confirm Word content type, walk entries lazily, and enforce actual expanded byte counts before invoking Mammoth. Reject unsafe paths, encrypted entries, duplicate or ambiguous entry names, and unsupported archives. Render extracted text as plain text. [PDF.js API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html) · [Mammoth raw text and security](https://github.com/mwilliamson/mammoth.js#extracting-raw-text) · [yauzl stream bounds](https://github.com/thejoshwolfe/yauzl#openreadstreamentry-options-callback)
- Start with **10 MiB per document, 20 resumes per browser selection, two concurrent uploads per browser, two admitted upload requests in the app, 30 requests per minute per HR account, and 100 pending or active documents across the local application**. Reject excess admission with `429` and `Retry-After`, and reserve backlog capacity atomically with the pending record. Check request size, time, and DOCX entry count on the server even when the browser has validated the file. Run one parse per worker with **50 PDF pages, 50 MiB total expanded DOCX content, 1,000 ZIP entries, 150,000 text characters, and 15 seconds of parser time** as starting limits. Run decompression and normalization in a killable child with a sanitized environment, bounded stdout/stderr, a heap ceiling, and a measured local worker container memory limit. Pass only the bounded input and exclude storage and database credentials. Bound S3 download bytes and time and verify SHA-256 before parsing. Treat the child as resource containment for local synthetic input. [Node child processes](https://nodejs.org/api/child_process.html)
- Keep upload availability, parse state, and candidate review distinct. Use `queued`, `processing`, `succeeded`, and `needs_manual_review` for stored documents and show retry progress while the job remains eligible. Store bounded plain text and optional deterministic suggestions separately from HR edits. Prefer one unambiguous email and explicitly recognizable name or experience. Leave uncertain values blank. Use stable failure reasons for scan-only files, invalid document contents, resource limits, and exhausted infrastructure retries. A stored original and its editable resume candidate survive worker extraction failure. For a failed JD parse, retain the original and show its status with the option to replace it.
- Jobs carry document ID, parse generation, and correlation ID, with no document content or personal fields. Fence worker writes by generation and claim token. Retry transient I/O failures twice with bounded backoff and commit permanent parse failures without retry. Reconcile against the recorded pg-boss job ID and current generation. Mark exhausted jobs or missing jobs past the retry window as needing manual review, and leave queued, delayed, retryable or active jobs eligible. Recover after restart with this same reconciliation. A retry or stale parser result must never overwrite candidate edits, revive an expired upload, or restore a replaced JD. Keep manual reprocessing outside this slice. [Worker entry point](../../apps/server/src/worker.ts) · [pg-boss](https://github.com/timgit/pg-boss)
- Let HR save partial drafts immediately, including during extraction. On confirmation, require a nonblank name and valid normalized email. Support optional nonnegative years of experience with one decimal digit, capped at 80. If two confirmations collide, translate the database conflict to a `409 duplicate_email` with the existing confirmed candidate’s ID. Let HR correct the email or link the draft to that confirmed candidate as a duplicate. Preserve its original file and exclude duplicates from the confirmed list and Slice 4 eligibility. Check both revisions, the drive, and the matching normalized email in the duplicate transaction. Apply validation and uniqueness again when HR edits a confirmed candidate.

### 4. Replace the Drives placeholder in the staff shell

- Keep `/staff/drives` as the list and add `/staff/drives/:driveId` as the detail route. Update Hono’s SPA entry routes so reloads and direct navigation work in the built app while API routes retain their existing handling. Reuse Base UI shadcn components and the PwC-inspired tokens. Keep the authenticated sidebar mounted and manage form, queue and polling state inside the Drives feature. [Current staff layout](../../apps/web/src/staff/staff-layout.tsx) · [shadcn Base UI Table](https://ui.shadcn.com/docs/components/base/table)
- Give HR a **New drive** action and a drive detail with sections for the job description, resume intake, and scorecard skills. The resume section shows each file’s progress, candidate review state, and next action. Provide accessible file selection, per-row errors and retry for transport failures, and manual editing for parse failures. Use a visible confirmation action, a duplicate-resolution choice, and file download. Preserve in-progress form values during background status refreshes and navigation conflicts.
- Show Directors the same drive names, overview totals, and read-only skill sets. Load intake and candidate data only for HR. Reject a Panelist route before fetching any drive data from the browser. Poll visible pending items through one bounded request, back off on temporary failures, and stop when work settles or the route, role or session changes. Clear feature data on identity or access changes so an earlier response cannot be shown in a different session or role. Test small screens, keyboard navigation and visible focus in both themes.

## Local acceptance

| Check | Required evidence |
| --- | --- |
| Upgrade and restart | Migrate existing Slice 2 data and a fresh isolated Compose stack, run seed twice, and preserve staff and fixture integrity. Reload a drive via the built Hono app. Restart the worker during an intake and verify a terminal outcome. |
| Permission boundaries | HR can complete the workflow. A Director can list and inspect the overview, receives no candidate details, filenames, extracted text, object keys or download links, and is denied mutations and originals. A Panelist sees no Drives item, a deep link returns to Dashboard before drive data is requested, and every targeted API read, write and download fails. Verify anonymous access, cross-drive IDs, and a stale client role against the server. |
| Intake and recovery | In one batch, process a text PDF, a valid DOCX with a duplicate case-variant email, and an unreadable scan. Correct or link the duplicate, manually enter the scan, and verify an authorized download matches the original checksum. Reject mismatched and oversized bodies, including streaming bodies without a declared size, without producing objects or candidates. Show manual review for an accepted DOCX that exceeds the decompression budget. Verify upload concurrency and rate limits return retry guidance while healthy files remain usable. |
| Consistency | Replay drive creation and uploads, race same-drive confirmations, and verify the same email confirms in another drive. Race a manual edit against parsing and a stale browser edit against a newer one. Simulate a lost response, S3 and enqueue failures, a delayed retry, and stale worker results. Race upload expiry with publication, test a delayed object write after cleanup, and race two JD replacements. Verify the winning JD is downloadable and the previous JD survives an unsuccessful replacement. Verify one candidate per accepted resume and preserve referenced objects through cleanup. |
| Skills, UI, and operations | Add, reorder, and review both skill sets, then edit one and verify its review resets. Exercise desktop and mobile HR and Director screens. Run Biome, TypeScript, Vitest with PostgreSQL, the production build, Playwright with separate Mailpit-backed staff sessions, and the existing Compose storage and worker smoke tests. Verify that logs contain identifiers and error classes only, with no filenames, email addresses, file contents or credentials. |

## Readiness decisions

The access defaults follow the product’s HR ownership and Director oversight split. Directors can read the overview and skills, and HR handles source documents and candidate edits. The limits above are local starting values and should be checked against synthetic samples and measured Docker resources before wider use. Approved retention periods, real-file handling, and deployment remain later gates. The parser and SeaweedFS permission checks are the first implementation gates and can be exercised with the existing local stack.
